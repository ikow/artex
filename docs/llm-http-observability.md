# 模型 HTTP 请求与限流监控

在 **模型配置 → 限流监控** 查看最近 1 小时、24 小时或 7 天的记录。页面每
30 秒刷新，也支持手动刷新。数据从功能启用后的第一次 HTTP 尝试开始记录；
不会把旧日志行回填为请求数。

## 统计含义

- **HTTP 尝试**：每次底层 HTTP 请求，包括 SDK 自动重试。流式、非流式和
  UI 连接测试都记录。多个模型或配置可能共享服务商配额。
- **429 响应**：上游原始 HTTP 429 数量，包含随后被本地余额不足逻辑转换为
  402 的响应。某些 429 表示预算限制，而非每分钟限流，应结合响应头判断。
- **429 比例**：429 / 收到 HTTP 响应的尝试数。未收到响应的网络错误不计入分母。
- **HTTP 错误**：所有 4xx/5xx 响应，包含 429。
- **网络错误**：没有收到 HTTP 响应的尝试。
- HTTP 200 不等于模型调用或任务成功；响应头之后的流错误仍应查看现有用量
  账本和任务日志。本监控不读取流正文。
- **SDK 内部重试**：同一次 Recorder 调用中，第 2 次及以后的 HTTP 尝试。
  上层任务重新发起的模型调用有新的调用 ID，不计为此指标的内部重试，但其
  每次 HTTP 请求仍会计入总请求数和 429 数。
- **本地节流**：当前配置的请求频率，不是服务商配额。
- **网关响应头**：最近一次实际观察到的限额、用量、剩余量、重置时间和
  `Retry-After`，附采集时间。它们是历史快照，不保证仍然有效；未返回即未知。
  `Retry-After` 支持秒数和 HTTP 日期格式，页面保留原值，避免误解单位。

## 数据与接口

`GET /api/llm/http-stats?hours=24` 使用现有认证，`hours` 接受 1–168。
响应包含 `since`、`as_of`、`tracking_since`、`models` 和最多 20 条
`recent_limits`。查询窗口外的请求不进入窗口统计。

`llm_http_attempts` 保存模型、配置名、任务/工作者、调用 ID、尝试序号、
原始状态码、请求到响应头的耗时以及经过白名单和格式验证的限流响应头。
它不保存请求 URL、任意请求/响应头、原始错误文本、提示词、响应正文、
Cookie 或凭据，也不会开启完整 LLM 正文录制。限额事件另以
`[llm-rate-limit]` 标签写入现有服务日志，每个原始 429 一条。

与现有用量账本一样，记录持久化到 PostgreSQL；本功能不自动删除历史数据。
写入失败不会中断模型调用，但会输出 `[llm-http]` 警告，这类尝试可能未进入统计。
本功能只观察，不更改网关配额、退避策略、并发设置或任务状态。

## 验证

将 `ARTEX_PG_DSN` 指向**专用测试数据库**，不要使用带有实际任务的数据库：

```sh
CGO_ENABLED=0 go test ./llmrec ./agent ./db ./server \
  -run '^Test(HTTP|QuotaAwareTransport|IsQuotaExhaustedMessage|Capture)'
cd web
npm run build:static
```

测试使用本地 HTTP fixture，不访问真实模型或扫描目标，覆盖 429→重试→成功、
流式正文不被消费、状态码归一化前计数、正文录制关闭、连接测试、时间窗口、
响应头隐私过滤和接口认证。
